# План развёртывания после аренды VPS

VPS уже арендован: **AdminVPS, Нидерланды**. Выбор провайдера завершён. Этот файл описывает дальнейший путь; успешный запуск агента и эксперименты ещё не подтверждены.

Обозначения: `VPS_IP` заменить адресом сервера. Команды помечены местом выполнения: **Mac** или **VPS**. Примеры используют SSH-порт 22 и пользователя `hermeslab`; если провайдер выдал другой порт или уже создал обычного пользователя, учитывать реальные значения.

## 1. Подключиться и проверить сервер

В кабинете AdminVPS найти IP, SSH-порт, имя пользователя и способ первого входа. Если выдан root, на **Mac**:

```bash
ssh root@VPS_IP
```

Для другого порта: `ssh -p PORT root@VPS_IP`. При первом входе сверить fingerprint SSH-хоста с доступными данными провайдера. Пароль вводится в терминале и не отображается; присылать его в чат не нужно.

На **VPS** выполнить:

```bash
cat /etc/os-release
id
uname -m
free -h
df -h /
```

Сохранить вывод для отчёта. Скрипты проекта рассчитаны на **Ubuntu 22.04+**; предпочтительна 24.04 LTS. Если установлена другая ОС, сначала адаптировать установку. Не переустанавливать сервер с данными автоматически. Записать тариф, CPU/RAM/диск и фактическую стоимость аренды из кабинета, не подставлять предполагаемые характеристики.

## 2. Настроить отдельный SSH-ключ

Если отдельного ключа для лабораторной ещё нет, на **Mac** создать его. Если файлы с таким именем уже существуют, использовать существующий ключ либо выбрать новое имя, не перезаписывать их:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/hermes_lab -C "hermes-agent-lab"
cat ~/.ssh/hermes_lab.pub
```

На **VPS** в первоначальной root-сессии:

```bash
install -d -m 700 /root/.ssh
nano /root/.ssh/authorized_keys
chmod 600 /root/.ssh/authorized_keys
```

Добавить строку из `.pub` отдельной строкой, сохранив уже имеющиеся ключи. Приватный файл без `.pub` остаётся на Mac. В новом терминале **Mac** проверить:

```bash
ssh -i ~/.ssh/hermes_lab root@VPS_IP
```

Если провайдер уже выдал обычного пользователя, добавить публичный ключ в его `~/.ssh/authorized_keys` и проверить вход под ним. До отключения парольного/root-входа обязательно проверить новую сессию по ключу.

## 3. Создать обычного пользователя

Если обычный пользователь с sudo уже есть, использовать его и пропустить создание. Иначе на **VPS**, пока от root:

```bash
apt-get update
apt-get install -y sudo
adduser hermeslab
usermod -aG sudo hermeslab
install -d -m 700 -o hermeslab -g hermeslab /home/hermeslab/.ssh
install -m 600 -o hermeslab -g hermeslab /root/.ssh/authorized_keys /home/hermeslab/.ssh/authorized_keys
```

`adduser` предложит задать локальный пароль для sudo. На **Mac** открыть ещё одну сессию:

```bash
ssh -i ~/.ssh/hermes_lab hermeslab@VPS_IP
```

В ней на **VPS**:

```bash
id
sudo -v
```

Проверить, что текущий UID не равен 0. Первую root-сессию оставить открытой до завершения проверки SSH. Последующие скрипты запускать под обычным пользователем, а не через `sudo bash`.

## 4. Перенести проект на VPS

Репозиторий приватный. Чтобы не сохранять GitHub-токен на сервере, отправить файлы из актуальной локальной Git-копии. На **Mac**, из папки проекта:

```bash
cd /Users/anvisero/Documents/ChatGPT/pyweb2
git log -1 --oneline
git archive --format=tar HEAD | ssh -i ~/.ssh/hermes_lab hermeslab@VPS_IP 'mkdir -p ~/hermes-agent-lab && tar -xf - -C ~/hermes-agent-lab'
```

В архив попадают закоммиченные файлы, без локальных секретов и runtime-данных. Перед отправкой незакоммиченных правок сначала сохранить нужные изменения в Git. Для нестандартного порта добавить `-p PORT` к SSH-команде. Если используется другой обычный пользователь, заменить `hermeslab`.

На **VPS**:

```bash
cd ~/hermes-agent-lab
ls -la
```

Должны присутствовать `compose.yaml`, `README.md`, `scripts/`, `docs/`, `skills/`, `templates/` и `tests/`. Передача архивом не переносит `.git`: история и дальнейшие изменения остаются на Mac/GitHub.

## 5. Подготовить Ubuntu, Docker и firewall

На **VPS** под обычным пользователем:

```bash
cd ~/hermes-agent-lab
bash scripts/bootstrap-host.sh
```

Скрипт обновляет пакеты, устанавливает Docker/Compose, включает Docker при загрузке и настраивает UFW. Он рассчитан на порт SSH **22**. Если используется другой порт, сначала адаптировать проверку и правило firewall в скрипте; не переключать порт вслепую и не удалять рабочий доступ. При наличии firewall провайдера разрешить нужный порт со своего IP и сохранить исходящий интернет.

После успешного bootstrap выйти из обычной SSH-сессии и подключиться заново, чтобы применилось членство в группе Docker. Затем на **VPS**:

```bash
cd ~/hermes-agent-lab
bash scripts/harden-ssh.sh
docker run --rm hello-world
docker compose version
sudo systemctl is-enabled docker
sudo ufw status verbose
sudo sshd -T | grep -E 'passwordauthentication|kbdinteractiveauthentication|permitrootlogin|pubkeyauthentication'
```

`harden-ssh.sh` запрещает парольный и root-вход только после проверки конфигурации. Оставить существующие сессии открытыми, открыть ещё один SSH-вход по ключу под обычным пользователем и убедиться, что он работает. При Match-блоках проверить эффективные SSH-настройки для фактического подключения отдельно.

Проверить исходящие подключения на **VPS**:

```bash
curl -IL --max-time 20 https://api.telegram.org
curl -fsS --max-time 20 https://openrouter.ai/api/v1/models -o /tmp/p1-models.json
```

HTTP-ответ Telegram подтверждает сетевой маршрут, но не работу бота. Окончательная проверка — диалог после настройки gateway. Сохранить вывод и реальные ошибки в журнал.

## 6. Подготовить Telegram и LLM

- Через `@BotFather` создать бота и сохранить токен. Узнать собственный числовой Telegram ID.
- В OpenRouter создать отдельный API-ключ. Выбрать доступную модель с tools и контекстом ≥64K. Для бесплатного варианта проверить нулевые цены prompt/completion в [каталоге](https://openrouter.ai/api/v1/models).
- **До запуска агента** установить числовой лимит расходов для ключа в панели провайдера и сделать скриншот без секретов. Бесплатный режим и нулевой баланс не заменяют настроенный лимит.
- Если LLM должна оставаться бесплатной, не пополнять баланс, отключить автопополнение, проверить fallback/auxiliary-модели и не подключать платные инструменты.

Сначала проверить короткий запрос модели. Квоты запросов независимы от денежного лимита; один ответ агента может потребовать несколько вызовов LLM. На `429` учитывать `Retry-After` и не повторять запросы непрерывно. [Лимиты OpenRouter](https://openrouter.ai/docs/api_reference/limits).

Токены вводить в мастер Hermes на VPS. Они сохраняются в `data/.env`, который исключён из Git. Не отправлять приватные ключи и токены в чат или репозиторий.

## 7. Настроить и запустить контейнер

```bash
bash scripts/init.sh
bash scripts/setup.sh
```

`init.sh` закрепляет образ через RepoDigest. Совпадающие UID/GID нужны для доступа владельца VPS к своим `data/` и `workspace/`. В мастере указать OpenRouter, free-модель, Telegram и свой ID. Allow-all и доступ групп оставить отключёнными.

В Compose явно задано `HERMES_WRITE_SAFE_ROOT: "/opt/data:/workspace"`. Официальный образ по умолчанию разрешает файловым инструментам запись только в `/opt/data`; одного mount и `terminal.cwd` недостаточно для записи в `/workspace`.

При обновлении этой переменной в уже работающем развёртывании сначала сохранить старый лог, затем на VPS пересоздать контейнер:

```bash
docker compose config -q
docker compose up -d --force-recreate hermes
bash scripts/verify.sh
```

Обычный `restart` не применяет изменённые переменные Compose. Пересоздание сохраняет каталоги `data/` и `workspace/`; мастер setup заново проходить не требуется. [Документация ограничения записи](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/reference/environment-variables.md#hermes_write_safe_root).

Не менять штатный entrypoint: `/init` официального образа выполняет подготовку с root, затем запускает gateway от непривилегированного пользователя. Это нужно проверить по `docker top`, а не только по пользователю внутри `docker exec`.

В `data/config.yaml` проверить основную модель, auxiliary-модели, fallback и доступные toolsets. В `hermes tools` выбрать бесплатные web_search и web_extract. Не подключать платный backend ради прохождения smoke test.

```bash
bash scripts/start.sh
bash scripts/verify.sh
bash scripts/status.sh
bash scripts/collect-evidence.sh first-start
```

Проверить логи активного Telegram gateway и ненулевой список навыков. Секреты в `data/.env`, а не в YAML или Git.

## 8. Проверить диалог, инструменты, память и навык

Отправить боту `/start`, обычный вопрос, затем запрос текущего UTC-времени через инструмент. Измерить время от отправки до ответа. Запустить `smoke-test.sh` и проверить реальные tool calls; одной фразы модели «готово» недостаточно.

На VPS сохранить вывод повторного теста отдельно от первого:

```bash
mkdir -p evidence
set -o pipefail
bash scripts/smoke-test.sh 2>&1 | tee evidence/p1-smoke-after-safe-root-fix.txt
cat workspace/p1-smoke.txt
```

Скрипт печатает уникальный маркер `P1-FILE-OK ...` и проверяет, что именно он записан в `/workspace/p1-smoke.txt` в текущем запуске. Файл на VPS доступен как `workspace/p1-smoke.txt`. Запись в `/opt/data/p1-smoke.txt` не заменяет эту проверку. Даже при успешной проверке файла отдельно подтвердить в трассе вызовы terminal, файловых инструментов, web_search и web_extract.

Изменить `data/memories/USER.md` и `MEMORY.md` под свою исследовательскую задачу. Записать в память уникальный несекретный маркер, например `P1-LAB-7319`. После `/new` спросить о маркере и предпочтениях, не раскрывая ответа в вопросе.

Собственный навык хранится в `skills/research-source-review/SKILL.md`; setup копирует его в `data/skills/` только если копии ещё нет. После последующих правок перенести обновлённый SKILL.md в runtime-каталог и перезапустить gateway. Проверить через Telegram `/research-source-review URL` и сохранить загрузку навыка и результат.

## 9. Проверить посторонний аккаунт

С другого собственного тестового аккаунта отправить боту `UNAUTHORIZED-P1-7319`. Сохранить скриншот отказа/запроса pairing без одобрения и серверный лог отказа. Если бот молчит, подтвердить отклонение в логах, а рядом по времени получить успешный ответ с основного аккаунта. Не разрешать сопряжение постороннему аккаунту.

Проверка dotenv в проекте — предварительная. Фактические настройки Hermes могут иметь иной приоритет; убедиться, что в config нет расширяющих доступ правил. Контрольный опыт обязателен.

## 10. Проверить reboot

```bash
bash scripts/collect-evidence.sh before-reboot
sudo reboot
```

После восстановления SSH:

```bash
cd ~/hermes-agent-lab
bash scripts/status.sh
bash scripts/collect-evidence.sh after-reboot
```

Не выполнять start/up после reboot. Сопоставить изменившийся boot_id, время загрузки VM и StartedAt контейнера, затем получить ответ бота. До reboot не выполнять stop/down: для намеренно остановленного контейнера `unless-stopped` не обещает запуск.

## 11. Проверить cron при закрытом клиенте

```bash
bash scripts/create-demo-cron.sh YOUR_PRIVATE_CHAT_ID
```

Сохранить ID и время одноразового задания. Закрыть Telegram на всех устройствах, отключить SSH, подождать 12–15 минут. Открыть клиент, сохранить сообщение, затем:

```bash
bash scripts/hermes.sh cron runs JOB_ID --limit 5
bash scripts/collect-evidence.sh closed-client-cron
```

Разделить время исполнения и время просмотра результата. Для усиления доказательства записать экран закрытия/открытия клиента. Не подменять плановое исполнение ручным `cron run`. Проверить файл `workspace/autonomy-check.log`; задача одноразовая и не должна бесконечно расходовать квоту.

## 12. Сохранить и оформить

Docker-логи: 5 файлов по 10 МБ. Это ограничение размера, а не срока. Внутренние `data/logs/` имеют отдельную политику; проверить её и при необходимости настроить logrotate на хосте. Архивы evidence выгружать после каждого этапа, хранить до сдачи + 30 дней.

`collect-evidence.sh` фиксирует exit code каждой команды: ненулевой код означает, что часть доказательств не собрана. Он скрывает известные секреты, но личные сообщения и идентификаторы требуют ручного просмотра. Не публиковать весь каталог data. Очищенные материалы для сдачи можно приложить отдельно; приватный evidence исключён из Git.

Заполнить [отчёт](report.md), [журнал отладки](debugging-log.md) и [чек-лист](evidence-checklist.md) только реальными результатами.
